GPU Cache Hierarchy: Understanding L1, L2, and VRAM

How memory access patterns affect texture fetch cycles and shader performance

gpuoptimizationmemorytexturesperformance

Every texture sample in your shader triggers a memory request. Whether that request takes 4 cycles or 400+ cycles depends entirely on where the data lives in the GPU's memory hierarchy. Understanding cache behavior isn't just academic—it's the difference between 60fps and 30fps in texture-heavy shaders.

TL;DR — Quick Reference

GPU Memory Hierarchy At a Glance text 
┌──────────────────┬─────────────┬──────────────────┬───────────────┐
│ Memory Level     │ Latency     │ Size (per SM)    │ Bandwidth     │
├──────────────────┼─────────────┼──────────────────┼───────────────┤
│ Registers        │ ~1 cycle    │ 256KB            │ ~20 TB/s      │
│ L1 Cache         │ ~30 cycles  │ 128-192KB        │ ~12 TB/s      │

└──────────────────┴─────────────┴──────────────────┴───────────────┘

Key insight: L1 hit = ~30 cycles, VRAM miss = ~500 cycles → 15x difference!

The Memory Hierarchy

Modern GPUs organize memory into a hierarchy of increasingly larger but slower storage. At the top sit registers—blazingly fast but severely limited. Below them, L1 and L2 caches act as staging areas for frequently accessed data. At the bottom, VRAM holds all your textures, buffers, and render targets.

  • Registers: ~1 cycle access, 256KB total per SM (shared across thousands of threads)
  • L1 Cache: ~28-35 cycles, 128-192KB per SM, dedicated to each streaming multiprocessor
  • L2 Cache: ~150-200 cycles, 4-40MB shared across all SMs, unified memory controller
  • VRAM (GDDR6/HBM): ~400-800 cycles, 8-24GB, massive bandwidth but high latency

Cache Lines and Spatial Locality

When you sample a single texel, the GPU doesn't fetch just that one pixel. It fetches an entire cache line—typically 32 or 64 bytes of contiguous memory. For RGBA8 textures, that's 8-16 texels. This design exploits spatial locality: pixels near each other in UV space tend to be accessed together.

Coherent vs Incoherent Texture Sampling glsl 
// GOOD: Coherent access - neighboring fragments sample neighboring texels
vec4 color = texture(uTexture, vTexCoord);

// BAD: Random access - cache thrashing, every sample misses
vec2 randomUV = hash2D(gl_FragCoord.xy); // Random UV per pixel
vec4 color = texture(uTexture, randomUV); // Cache line wasted

// UGLY: Dependent reads - latency stacking
vec2 offset = texture(uOffsetMap, vTexCoord).xy; // First fetch
vec4 color = texture(uTexture, vTexCoord + offset); // Must wait!

The Warp and Cache Coalescing

GPUs execute threads in groups called warps (NVIDIA, 32 threads) or wavefronts (AMD, 32-64 threads). When all threads in a warp access memory at the same time, the hardware tries to coalesce these requests into as few cache line fetches as possible. Perfect coalescing means 32 threads hitting the same cache line—one fetch serves everyone.

Fragment shaders naturally achieve good coalescing because GPU rasterizers process pixels in 2x2 quads, and quads are grouped into tiles that map to consecutive threads. When you sample a texture at the interpolated UV, neighboring fragments sample neighboring texels—perfect spatial locality.

What Causes Cache Misses?

  • Random UVs: Procedural distortion, noise-based sampling, stippling patterns
  • Dependent texture reads: UV offset stored in another texture (parallax, flow maps)
  • Large UV jumps: Sampling distant mip levels, cubemap edge cases
  • Texture thrashing: Too many unique textures accessed in same shader pass
  • Working set overflow: Total active texture data exceeds L2 capacity

Mipmapping: The Cache's Best Friend

Mipmaps aren't just for visual quality—they're a cache optimization. When a surface is far from the camera, sampling the full-resolution texture would fetch distant texels that span many cache lines. The mipmap's smaller footprint keeps samples spatially coherent and cache-friendly.

Explicit LOD for Cache Control glsl 
// Auto mip selection (usually correct)
vec4 color = texture(uTexture, uv);

// Force lower-res mip for cache efficiency in blur passes
// Saves bandwidth when you&#39;re averaging anyway
vec4 color = textureLod(uTexture, uv, 2.0); // Mip level 2

// Bias toward higher mips (cache-friendly, softer)
vec4 color = texture(uTexture, uv, 1.0); // +1 mip bias

// textureGrad: Explicit derivatives for anisotropic filtering
// Controls footprint precisely for cache-aware sampling
vec4 color = textureGrad(uTexture, uv, dFdx(uv) * 0.5, dFdy(uv) * 0.5);

Measuring Cache Efficiency

GPU profilers like NVIDIA Nsight, AMD Radeon GPU Profiler, and RenderDoc expose cache hit rates and memory throughput. Key metrics to watch:

  • L1 Hit Rate: Should be >80% for well-optimized shaders. Below 60% indicates access pattern problems.
  • L2 Hit Rate: Measures working set fit. Below 70% suggests texture thrashing or too many unique textures.
  • Texture Memory Throughput: Compare to theoretical max. Low throughput with high latency = cache misses.
  • Memory-bound vs Compute-bound: If memory is the bottleneck, cache optimization has highest impact.

Texture Fetch Latency Hiding

GPUs hide memory latency through massive parallelism. While one warp waits for texture data, the scheduler switches to another warp that's ready to execute. This is why occupancy matters: more warps in flight means more opportunities to hide latency.

Prefetching Texture Data glsl 
// Strategy: Issue all texture fetches early, do math while waiting

// Issue fetches immediately (non-blocking)
vec4 albedo = texture(uAlbedo, uv);       // Fetch 1
vec4 normal = texture(uNormal, uv);       // Fetch 2
vec4 roughness = texture(uRoughness, uv); // Fetch 3
vec4 ao = texture(uAO, uv);               // Fetch 4

// Do expensive math while waiting for textures
vec3 N = normalize(vNormal);
vec3 V = normalize(uCameraPos - vWorldPos);
vec3 L = normalize(uLightPos - vWorldPos);
vec3 H = normalize(V + L);
float NdotL = max(dot(N, L), 0.0);
float NdotV = max(dot(N, V), 0.0);
float NdotH = max(dot(N, H), 0.0);

// By now, texture fetches have likely completed
// Using the data doesn&#39;t stall
vec3 albedoColor = albedo.rgb;

Texture Memory Layout

GPUs store textures in Morton order (Z-order curve) or similar space-filling curves, not linear row-by-row. This layout keeps 2D-local texels close in memory, improving cache efficiency for typical sampling patterns.

Texture swizzling happens automatically when you upload textures via the graphics API. Never manually 'optimize' texture data layout—the driver handles this based on GPU-specific tiling patterns.

Practical Optimization Strategies

1. Texture Atlasing

Packing multiple textures into one atlas keeps related data in the same cache space. When sampling from an atlas, neighboring draw calls often hit already-cached data. The tradeoff: more complex UV math and potential filtering artifacts at tile boundaries.

2. Channel Packing

Channel Packing for Fewer Fetches glsl 
// BAD: 4 separate texture fetches (4x memory traffic)
vec4 albedo = texture(uAlbedo, uv);     // RGBA
float rough = texture(uRoughness, uv).r; // R (wastes GBA)
float metal = texture(uMetallic, uv).r;  // R (wastes GBA)  
float ao = texture(uAO, uv).r;           // R (wastes GBA)

// GOOD: 2 fetches with packed data
vec4 albedo = texture(uAlbedo, uv);      // RGB = color, A = unused
vec4 orm = texture(uORM, uv);            // R = AO, G = Roughness, B = Metallic
float ao = orm.r;
float rough = orm.g;
float metal = orm.b;

3. Reduce Dependent Reads

Dependent texture reads—where the UV comes from another texture—serialize memory access. The GPU can't prefetch the second texture until the first completes. Minimize these chains or compute UVs mathematically when possible.

4. Bindless Textures

Traditional texture binding forces driver overhead and limits cache utilization across draw calls. Bindless textures (via GL_ARB_bindless_texture or Vulkan descriptor indexing) keep all textures resident and accessible, improving cache reuse across the frame.

Architecture Differences

Cache behavior varies significantly between GPU vendors and generations. NVIDIA's L1 is tightly coupled with shared memory, AMD's Infinity Cache adds another hierarchy level, and mobile GPUs often have smaller but more specialized caches optimized for tiled rendering.

Profile on your target hardware. Desktop optimizations may hurt mobile performance and vice versa. AMD's cache hierarchy differs enough from NVIDIA that vendor-specific tuning often pays off.

Quick Wins: Copy-Paste Patterns

Here are battle-tested patterns you can apply immediately to improve cache efficiency in your shaders.

Pattern 1: ORM Texture Packing glsl 
// Pack Occlusion, Roughness, Metallic into one texture
// BEFORE: 3 texture fetches (wasteful)
float ao = texture(uAO, uv).r;        // Only uses R channel
float rough = texture(uRough, uv).r;  // Only uses R channel
float metal = texture(uMetal, uv).r;  // Only uses R channel

// AFTER: 1 texture fetch (3x faster)
vec3 orm = texture(uORM, uv).rgb;
float ao = orm.r;
float rough = orm.g;
float metal = orm.b;
Pattern 2: Early Texture Prefetch glsl 
// Issue ALL texture fetches first, then do math
void main() {
    // === FETCH PHASE (non-blocking) ===
    vec4 albedo   = texture(uAlbedo, vUV);
    vec4 normal   = texture(uNormal, vUV);
    vec4 orm      = texture(uORM, vUV);
    vec4 emissive = texture(uEmissive, vUV);
    
    // === COMPUTE PHASE (hides latency) ===
    vec3 N = decodeNormal(normal.xy);
    vec3 V = normalize(uCameraPos - vWorldPos);
    vec3 L = normalize(uLightDir);
    vec3 H = normalize(V + L);
    
    float NdotL = max(dot(N, L), 0.0);
    float NdotV = max(dot(N, V), 0.0);
    float NdotH = max(dot(N, H), 0.0);
    float VdotH = max(dot(V, H), 0.0);
    
    // === USE PHASE (textures ready by now) ===
    vec3 F0 = mix(vec3(0.04), albedo.rgb, orm.b);
    // ... rest of PBR calculation
}
Pattern 3: Mip Bias for Blur Passes glsl 
// When doing blur/downsample, use higher mip levels
// This saves bandwidth since you&#39;re averaging anyway

// Standard blur (fetches full-res texels)
vec4 blur = vec4(0.0);
for (int i = 0; i < 9; i++) {
    blur += texture(uTexture, uv + offsets[i]) * weights[i];
}

// Cache-friendly blur (uses lower mip = fewer cache lines)
vec4 blur = vec4(0.0);
float mipBias = 1.0; // Use mip level 1 (half res)
for (int i = 0; i < 9; i++) {
    blur += texture(uTexture, uv + offsets[i], mipBias) * weights[i];
}

Combine these patterns: Pack your PBR textures into ORM format, prefetch all at shader start, and use mip bias in post-processing passes. This alone can yield 20-40% improvement in texture-heavy shaders.

Key Takeaways

  • Cache hits are ~15x faster than VRAM fetches (30 vs 500 cycles). Coherent access patterns are critical for performance.
  • Mipmapping isn't optional—it's a cache optimization that keeps your working set manageable.
  • Pack related data into fewer textures. Four 1-channel fetches cost more than one 4-channel fetch.
  • Issue texture fetches early and do math while waiting. GPUs hide latency through parallelism.
  • Avoid dependent texture reads when possible. Each dependency serializes memory access.
  • Profile with Nsight/RGP—cache hit rates reveal optimization opportunities invisible to frame timing alone.

Don't micro-optimize without profiling. Cache behavior is complex and hardware-dependent. Measure first, optimize second, and verify improvements on actual target hardware.
